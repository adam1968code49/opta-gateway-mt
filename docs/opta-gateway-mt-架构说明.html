一句话版本。PLC 线程独占 EtherNet/IP 客户端，每 2 秒把 28 个传感器读进一个约 220 字节的纯数据快照，加锁拷贝一次发布出去；主线程独占全部云端属性和 ArduinoCloud.update()，每趟 loop 加锁把快照拷回来，序号变了就逐槽赋给云属性。两个线程各打各的心跳，喂狗线程取较旧的那条判断有没有卡死。任何一边阻塞，另一边照常工作。

1. 为什么要拆成两个线程

旧固件（opta-plc-gateway-ip2.ino，2587 行单文件）是单线程：loop() 里依次做 PLC 读取、云端 update()、日志、诊断。ArduinoIoTCloud 库在 update() 内部默认武装一个 32.76 秒 的硬件看门狗，并且只在 update() 里喂。于是 loop() 里任何一处超过 32 秒的阻塞都会让板子被硬件复位。

实测两处这样的阻塞：

阻塞点触发条件实测时长后果
eip.begin()（PLC 的 TCP 连接）PLC 断电或网线拔掉27.7 s逼近看门狗窗口；与其他延迟叠加即复位
ArduinoCloud.update() 内的 TLS 重连WiFi 通、但到 iot.arduino.cc 的链路断110 s 以上直接复位；过夜 6 次重启全部落在这里

先后加过三层缓解：独立喂狗线程、PLC 探针（先用 300 ms 的 TCP 敲门再 begin()）、云端探针（先敲 8885 端口再进 update()）。重启从 13–77 分钟一次降到 2–4 小时一次，但没归零，因为根子在于一个线程里放了两个各自都可能长阻塞的 I/O 对象。

结构性解法。把两个会阻塞的对象分到两个线程：EtherNet/IP 客户端归 PLC 线程，云端连接归主线程。一边阻塞只卡自己，喂狗线程仍能看到另一边活着。这就是 opta-gateway-mt。

设计原则（贯穿全部代码）

  • 每个可阻塞对象只有一个 owner。eip 只在 PLC 线程被调用；Cloud* 属性只在主线程被赋值。调试构建里有断言宏在违规时打印并自旋。
  • 跨线程只传纯数据。快照里没有 String、没有指针，用 static_assert(is_trivially_copyable) 在编译期锁死。原因：一个线程赋值 String 的同时另一个线程在序列化它，就是 use-after-free。
  • 锁里只做一次结构体拷贝。不做 I/O、不做分配。全仓库只有一把锁、四个持锁函数、每个的临界区就是一行拷贝。
  • 主线程永远不等 PLC 线程。命令队列用非阻塞的 try_alloc / try_get，队列满了就丢并计数。
  • 先敲门再进门。任何无界的 connect 之前，先用带超时的原生 TCP socket 探一下端口开不开。

为什么 PLC 线程要 16 KB 栈

旧固件里 pollSensors() 跑在主线程的默认栈上，加上 CIP 报文构造和 TLS，栈水位曾逼近告警。拆出来之后 PLC 线程只跑 CIP，16 KB 是保守取值；EtherNet/IP 客户端的收发缓冲是函数级 static，放在 .bss 不占栈；快照 w 约 220 字节在线程栈上。实际水位由 StackWatch 测量并放进快照的 plcStackFree 字段（批 0 只在串口显示）。

调试期的归属断言

SHARED_ASSERT_ON_PLC();   // pollSensorsInto() 第一行：不在 PLC 线程上就打印并自旋
SHARED_ASSERT_ON_MAIN();  // cloudSideAssign() 第一行：不在主线程上就打印并自旋

g_plcThreadId 在线程体第一行记录，g_mainThreadId 在 setup() 里记录。ENABLE_SERIAL_DEBUG=0 时两个宏为空。违规后自旋，喂狗线程 60 秒后放手，硬件复位——在台架上是最响的失败，在现场也不会永久挂死。

5. 共享面 shared.h：两个线程唯一的接触点

所有跨线程的东西都在这一个文件里：一个 PLC→主的快照、一个主→PLC 的连续控制块、一个主→PLC 的一次性命令队列、一把锁。设计文档的判据是：以后的改动如果能不碰这个文件，说明线程边界画对了。

5.1 PlcSnapshot（PLC → 主，每拍一份）

字段类型含义
sequint32单调递增，每次发布 +1，在锁内递增，所以主线程不可能看到新序号配旧数据。
stampMsuint32发布时的 millis()。主线程用它算快照年龄，超过 3 拍（6 s）判定 PLC 线程卡住。
sensor[28]float28 个传感器值，槽序 = SENSOR_TAGS 顺序（见第 13 节）。
ok[28]bool这一拍哪些槽读到了。主线程只赋值 ok 为真的槽，读失败的属性保留上一个真值而不是变成 0。
failsint32本拍没读到的槽数。
plcConnectedboolEtherNet/IP 会话是否在。

lastCipStatusuint16最近一次 CIP 通用状态码。
lastError[48]char"ok" / "read fail x3 (cip=0x5)" / "plc not listening (probe)"。是 char[] 不是 String。

整个结构约 220 字节，static_assert(sizeof < 1024)；static_assert(is_trivially_copyable) 保证没有 String/指针混进来。

5.2 CtrlState（主 → PLC，连续）与 Cmd 队列（主 → PLC，一次性）

struct CtrlState {
  bool  controlEnabled;   // 批 1
  float flowRate;         // 批 2
  float flowBatch;        // 批 2
};
struct Cmd {
  uint16_t tag;     // CmdTag 枚举，24 项
  bool     isBool;
  float    value;
};
rtos::Mail<Cmd,16> g_cmdQueue;

批 0 没有人写它们，但结构第一天就定型，后面批次不必再改这个文件。命令队列是 mbed 的 Mail，16 槽；投递用 try_alloc，满了返回 false 并把 g_cmdDropped +1；取用 try_get，空了立刻返回。两端都不阻塞。

5.3 锁的规则

sharedPublish(w):  stampMs=millis(); lock(); w.seq=published.seq+1; published=w; unlock();
sharedTake(out,&lastSeq): lock(); out=published; unlock(); 若 out.seq==lastSeq 返回 false

一把 rtos::Mutex（带优先级继承）守两个结构体。四个持锁函数的临界区都只有一行结构体拷贝，微秒级。两把锁只会多出一种死锁方式，所以只用一把。

6. PLC 线程：每 2 秒一拍

图 6-1 PLC 线程的一拍。左分支是未连接时的重连门，右分支是已连接时的扫描。两条分支都以发布收尾，所以即使 PLC 掉线，快照也每 2 秒更新一次（带 plcConnected=false）。

扫描细节 pollSensorsInto(w)

  • 先把 28 个 ok[] 清零。
  • 22 个 REAL 用 Multiple Service Packet 批读：EIP_MAX_MSP_TAGS=12，分两组两次往返。结果按 REAL_SLOT[k] 散射进规范槽位。
  • 6 个 DINT（4 个热泵压力原始计数、2 个 DS 温湿度）单个读，raw × DINT_SCALE + DINT_OFFSET 后散射进各自槽位。
  • 统计 fails；失败集合变化时才在串口列出失败标签名（不是每拍都刷屏）。
  • 全部 28 个都失败 → eip.end()，置 plcConnected=false，下一拍进入重连门。

重连门

退避从 5 s 起，每次失败翻倍，上限 60 s，成功后复位。先探针再 begin：探针是原生 TCPSocket，set_timeout(300) 在 connect() 之前调用，netsocket 层对 connect 生效，所以 PLC 断电时一次尝试只花 0.3 s，而不是旧固件的 27.7 s。

7. 主线程：setup() 与 loop()

7.1 setup() 的顺序（每一步的位置都有理由）

7.2 loop() 的一趟

图 7-1 主线程 loop() 一趟。没有任何一步等待 PLC 线程。

cloudSideConsume() 每趟都调，但只有 seq 变化时才做 28 次赋值——所以云属性每 2 秒更新一次，与 PLC 拍同步，而不是每趟 loop 都刷。

8. 快照的一生：从 PLC 标签到云端属性

图 8-1 一拍数据的旅程。两次加锁各只拷一个结构体；String 只在主线程、在赋值瞬间构造。

槽位是合同

plc_tags.h 的 SENSOR_TAGS[] 顺序定义了槽 0–27。PLC 线程按这个顺序写 w.sensor[]，cloud_side.h 的 28 个 TAKE(i, 属性) 按同一顺序读。两边都靠这一张表；表的长度有 static_assert(N_SENSORS == 28) 把守，一对一配对的正确性在代码审查时逐槽核过（见第 13 节）。

"读失败不归零"

旧固件读失败时属性会被写成 0，看板上出现假的归零尖峰。现在 TAKE 只在 ok[i] 为真时赋值，失败的槽保持云端上一个真值，同时 fails、lastError 说明发生了什么。

云端只在变化时发

28 个传感器都注册为 READ, ON_CHANGE；压力、热泵压力和液位另加 PUB_DELTA 阈值抑制抖动。所以每 2 秒赋值 28 次并不等于每 2 秒发 28 条 MQTT，库只发变了的。

9. 喂狗线程：看两条心跳，怪较旧的那条

每 2000 ms：
  sinceMain = now - s_mainBeatMs       // 主线程每趟 loop 开头打一次
  sincePlc  = now - s_plcBeatMs        // PLC 线程每拍开头打一次
  since     = max(sinceMain, sincePlc)
  若 since 创新高：s_stallMaxMs = since；s_stallWhere = (sinceMain ≥ sincePlc) ? s_whereMain : s_wherePlc
  若硬件看门狗还没被武装：continue     // 它由 update() 内的云状态机武装，setup 末尾还没跑
  若 since < 60000：kick()             // 否则放手，s_wdRefusals++，硬件在 32.76 s 内复位

为什么取 max：只要有一个线程卡死，系统就已经不健康，喂狗线程不能替它遮掩。为什么 60 s 放手：一个永远不回来的线程比一次重启更糟；60 s 给合法的长操作（PLC 半死时一拍最坏约 24–28 s，主线程 DNS 全灭时一趟最坏约 30 s）留了约两倍余量。

位置码 WD_AT_*

每个线程在进入一段可能阻塞的代码前登记自己在哪。两个线程各有一个槽（s_whereMain/s_wherePlc），归因时取较旧心跳所属线程的槽。如果只用一个共享槽，健康线程会在每趟结束时把它覆盖成 NONE，卡死现场就丢了——这正是审查阶段改掉的一个缺陷。

2CLOUD主ArduinoCloud.update()。开机首次 TLS 连接约 6 s 就落在这里，所以云端 loopStallMs≈6000@2 是正常的
3USB—USB 日志（批 6，当前编译掉）

码本身就说明了线程：1、2、4、12 只出现在主线程，5–11、13 只出现在 PLC 线程。云端属性 stallWhere 发布的就是这个码。

已知局限。loopStallMs 只增不减：开机那次 6 s 的云连接会把它钉在 ~6000，之后一次 20 s 的停顿如果没超过历史最大值就看不见。批 1 计划改成滑动窗口。

10. 两个探针：先敲门，再进门

两处无界阻塞的共同病因是：Arduino 的 Client 在 connect() 期间是阻塞的，只在连接成功后才被设成非阻塞；对方不在时就跑满协议栈的 TCP 重传（约 28 s）。两个探针用同一个药方：用原生 mbed TCPSocket，在 connect() 之前 set_timeout()，netsocket 层对 connect 生效，然后只开一下、关掉，什么都不发。

PLC 探针 plc_probe.h
目标 192.168.102.21:44818，超时 300 ms。
何时：PLC 线程重连门内、eip.begin() 之前。
不通 → 不连、写 lastError="plc not listening (probe)"、退避翻倍。
代价：PLC 断电时一次尝试 0.3 s，而不是 27.7 s。
云探针 cloud_probe.h
目标 iot.arduino.cc:8885（MQTT/TLS 端口），超时 500 ms，DNS 结果缓存。
何时：主线程每趟 loop，只在"WiFi 已连、云未连"这一个状态才真敲；5 s 节流。
不通 → 这趟跳过 update()（反正只会卡住）。

云探针的门为什么这么窄

cloudUpdateAllowed(wifiUp, cloudUp, now):
  cloudUp   → true    // 已连：update() 负责发布、keepalive、OTA，绝不能跳
  !wifiUp   → true    // 无线断：update() 是唯一会重新关联射频的东西，跳了就永远离线
  否则（WiFi 通、云断）：每 5 s 敲一次 8885；敲通才 true

只有"WiFi 通、云断"这一个状态的下一次 update() 是那个无界的 TLS connect；其他状态的 update() 都很快或者必须跑。DNS 失败按"不通"处理：DNS 死通常意味着互联网断了，这时进 update() 只会白卡。

实测归因（改造前的过夜数据）

六次重启里有两次 WiFi 信号稳定在 -70 dBm 长达 8 分钟，说明掉的不是无线链路而是到 iot.arduino.cc 的上游。所以探针测的是"broker 端口能不能到"，而不是 RSSI 这个有三分之一时间指错方向的代理。

已知局限。DNS 失败时 s_brokerResolved 保持 false，每次敲门都重跑 gethostbyname（mbed 默认 5 s × 3 次），互联网断开期间主线程每 5 s 可能阻塞 15–30 s——仍在 60 s 放手线之内，但批 1 应缓存否定结果。

12. 四种故障与固件的反应

故障PLC 线程主线程 / 云端看板与串口上的样子
PLC 断电或网线拔掉下一拍 28 个全失败 → eip.end()；之后每拍走重连门：探针 0.3 s 拒绝，退避 5→10→20→40→60 s。每拍仍发布（plcConnected=false）。完全不受影响：update() 照常，诊断照常。cloudSideConsume 每 2 s 仍收到新 seq，传感器属性因 ok[] 全假而保持旧值。plcConnected=False，lastError="plc not listening (probe)"，eipMs≈300，uptimeS 持续更新；串口 seqAge<2500、cloud=up。PLC 回来后 60 s 内 "session OK"。
WiFi 或上游断完全不受影响：继续每 2 s 扫描发布。WiFi 断：门放行，update() 快速返回并重新关联。WiFi 通、云断：每 5 s 敲一次 8885，不通就跳过 update()，主线程不会卡进 TLS connect。看板全部属性停更（板子发不出去）；串口 wifi=down 或 cloud=down 但 plc=1、t1/lvl 继续变化、stall 不爬升。恢复后云端出现新值。
PLC 半死（端口开着、不回 CIP）探针通 → begin() 或读超时：每次 I/O 1500 ms 超时，一拍最坏约 24–28 s（两组 MSP + 6 单读），仍在 60 s 内。不受影响。快照年龄可能超过 6 s → plcStalled 为真，lastError="plc thread stalled Ns"，FAULT 灯亮。lastError 报 stalled；stall@6 或 @5 增大。这是终审点名最值得用串口验证的场景：readExact 每收一字节就重置计时，慢速滴答的对端理论上可拖长一拍。
某线程真的卡死（bug、死锁）喂狗线程看到该线程心跳超过 60 s → 停止踢狗 → 硬件在 32.76 s 内复位。s_stallWhere 记下卡死线程当时的位置码。重启后 bootReason 的 n 加一，云端 loopStallMs/stallWhere 在复位前的最后一次诊断里指向卡死段（如果那次诊断赶上发出去）。

15. 批 1 之前要知道的事

全分支终审（2026-09-04）认定两个隔离承诺在代码上成立、无需在过夜前修改；下面是它留给批 1 的清单，完整版在仓库 docs/batch0-final-review.md。

  1. panelLeds() 在 #if ENABLE_SERIAL_DEBUG 里——生产构建关掉串口后面板灯会全灭。移出来。
  2. shared.h 的全局对象是头文件里的 static：单翻译单元正确，第二个 .cpp 包含它会静默得到第二把锁。加一个非 static 守卫符号让它变成链接错误。
  3. PLC 线程一拍只在开头喂一次狗；批 1 加阀和状态字读取后一拍可能逼近 60 s。在每组 MSP、每个 DINT 读之后补 wdBeatPlc()。
  4. 云探针 DNS 失败不缓存，互联网断开时每 5 s 可能阻塞 15–30 s。缓存否定结果。
  5. plcStalled 在 PLC 线程尚未发布过任何快照时（stampMs=0）会误判；加 seq != 0 前置条件。
  6. 重连分支不清 ok[]，它保留上一拍的真值；批 2 水量核算不能把它当"本拍读到"。
  7. 归属断言只在 pollSensorsInto 一处；放进重连分支和 drainCommands()，或直接放进 EtherNet/IP 的 sendRRData()。
  8. LOG 两个线程都用：没接控制台时 USBSerial::write 立刻返回，零风险；接着控制台时是交叉乱码不是死锁；控制台停止排空时两线程可能一起卡住 60 s 后复位。给 LOG 加锁或让 PLC 线程不写串口。
  9. loopStallMs 只增不减。改滑动窗口。
  10. 没有编译期检查保证 28 个 TAKE 恰好覆盖 0–27 各一次。加 constexpr 位掩码断言。
  11. tools/build.sh 没有告警门。
  12. cloud_side.h 头注释"seven String properties"应改为一个。
批 1 上线前的一个陷阱。ArduinoIoTCloud 会在首次同步时把云端存着的可写属性值当 onChange 交下来。批 0 期间看板上的按钮仍能按、云端仍会存值、板子不消费；批 1 一连上云，那些存着的值（比如一次误按的 start）会瞬间发到 PLC。批 1 之前先把云端这些值归位。
回滚路径。旧固件没有归档二进制。回滚 = 在 opta-plc-gateway-ip2 里跑它的 tools/build.sh 再 OTA，或到板子跟前 DFU。

16. 术语表

术语解释
EtherNet/IP、CIPAllen-Bradley PLC 的以太网工业协议；CIP 是其上的通用工业协议，本固件用显式报文按标签名读写。端口 44818。
MSPMultiple Service Packet，一条 CIP 报文里打包多个读请求。本固件一组最多 12 个标签。
REAL / DINTCIP 数据类型：32 位浮点 / 32 位有符号整数。IP2 上 6 个点以 DINT 原始计数给出，固件乘缩放加偏移。
快照 PlcSnapshotPLC 线程一拍的全部结果，纯数据结构，约 220 字节，加锁整体拷贝。
seq快照序号。主线程凭它判断"有没有新的一拍"。
拍 tickPLC 线程的一个周期，2000 ms。
心跳 beat线程告诉喂狗线程"我还活着"的时间戳。
stall某线程自上次心跳以来的时间；喂狗线程取两线程中的较大值。
WD_AT_*位置码 0–13，线程在进入可能阻塞的段之前登记。
探针 probe带超时的原生 TCP 开关一次，只看端口有没有人听，不传数据。
Mailmbed RTOS 的定长消息队列（内存池 + 队列）。命令队列用它，16 槽。
trivially copyableC++ 类型特征：可以 memcpy 而不破坏语义（无 String、无指针、无虚函数）。快照的编译期门槛。
ON_CHANGE / PUB_DELTAArduinoIoTCloud 的属性更新策略：值变了才发 / 变化超过阈值才发。
n=KVStore 里的启动计数，出现在 bootReason 字串里。不变 = 没重启。
OTA经 Arduino Cloud 无线刷固件。回调返回 true 才允许应用。
StackWatch手工栈水位：刷图案、数没被覆盖的字。每线程一个实例。
KVStoreArduino 的键值持久存储（QSPI flash）。存 WiFi 凭据、启动计数。
